* Goal and invariants

Retrieval is a first-major-milestone package family, not deferred optional work. The design must support standalone retrieval, graph nodes, agent tools and direct RAG composition without forcing one database/vector backend.

Invariants:

1. Documents/chunks preserve source provenance.
2. Loader/splitter/embedding/vector-store implementations sit behind project-owned protocols.
3. Lazy paths are bounded and cancellation-aware.
4. Embedding dimensionality is validated before store mutation.
5. Similarity score meaning is explicit and backend-normalized where possible.
6. Metadata filters never silently change meaning when a backend cannot push them down.
7. Deterministic reference backends exist for tests and small workloads.
8. Retrieval never implicitly mutates the model prompt; applications/agents decide how retrieved context is consumed.

* Document

Canonical =document= fields:

- =id= — stable optional caller/source id;
- =page-content= — primary textual content for first milestone;
- =metadata= — JSON/Lisp map of source metadata;
- =source= — normalized URI/path/source identity where known;
- =mime-type=;
- =provenance= — loader/source/chunk parent information;
- extension map for loader-specific data.

Representative shape:

#+begin_src lisp
(defclass document ()
  ((id :initarg :id :initform nil :reader document-id)
   (page-content :initarg :page-content :reader document-page-content)
   (metadata :initarg :metadata :initform nil :reader document-metadata)
   (source :initarg :source :initform nil :reader document-source)
   (mime-type :initarg :mime-type :initform "text/plain"
              :reader document-mime-type)
   (provenance :initarg :provenance :initform nil
               :reader document-provenance)
   (extensions :initarg :extensions :initform nil
               :reader document-extensions)))
#+end_src

Document equality/id semantics do not silently hash all content. Applications may supply ids; loaders may derive deterministic ids from stable source records where appropriate.

** Provenance

A chunk produced from a parent document carries at least parent id/source and chunk ordinal/range where known:

#+begin_src lisp
'((:parent-id . "manual.txt")
  (:source . "file:///docs/manual.txt")
  (:chunk-index . 17)
  (:start-offset . 8021)
  (:end-offset . 8610))
#+end_src

Derived chunks must not lose the parent metadata needed to trace a model answer back to source material.

* Loader protocol

#+begin_src lisp
(defclass document-loader () ())

(defgeneric load-documents (loader &key context))
(defgeneric lazy-load-documents (loader &key context))
(defgeneric load-documents-async (loader &key context))
#+end_src

Contracts:

- eager load returns an ordered sequence of =document=;
- lazy load returns a Design 001 bounded channel/iterator whose terminal state is explicit;
- async eager load returns a project-owned future resolving to the same document sequence;
- loader failures are typed retrieval/loader conditions;
- cancellation/deadline comes from runtime context;
- eager and lazy outputs preserve the same logical order for deterministic sources.

Loader constructors hold source-specific configuration but never global credentials invisibly. Network loaders use runtime/transport configuration.

Initial built-ins:

**Text loader** — wrap supplied string/text with metadata.

#+begin_src lisp
(load-documents
 (make-text-loader "hello" :metadata '((:kind . :example))))
#+end_src

**File loader** — load text files with explicit encoding (UTF-8 default) and source path metadata; size ceilings required.

#+begin_src lisp
(make-file-loader #P"README.md"
                  :encoding :utf-8
                  :max-bytes (* 8 1024 1024))
#+end_src

**JSON loader** — parse Jzon values and use a caller-provided extraction path/function to map records/content/metadata.

#+begin_src lisp
(make-json-loader #P"records.json"
                  :records-path '("items")
                  :content-function (lambda (row) (gethash "text" row))
                  :metadata-function #'json-row-metadata)
#+end_src

**CSV loader** — row-per-document and whole-file modes with header metadata.

**HTML loader** — fetch or accept HTML and produce visible/textual content through a small extraction protocol. Do not attempt browser automation in the core loader.

**HTTP text loader** — fetch bounded textual resources through the common transport with content-type/size policy.

Binary/PDF/office loaders are extension integrations unless a safe maintained dependency is explicitly selected later. The protocol must accommodate them without core redesign.

* Lazy loader flow control

#+begin_src text
source producer
    |
    v
bounded document channel
    |
    +-- consumer receives -> continue
    +-- queue full -> producer backpressure
    +-- cancel/deadline -> producer cleanup + terminal event
#+end_src

No loader may hide an unbounded accumulator behind a “lazy” API.

* Splitter protocol

A splitter accepts documents or text and returns ordered document chunks with parent provenance.

#+begin_src lisp
(defclass text-splitter () ())

(defgeneric split-text (splitter text &key metadata context))
(defgeneric split-documents (splitter documents &key context))
#+end_src

Common config:

- chunk size;
- overlap;
- length function/tokenizer;
- separator set/strategy;
- metadata transformation;
- keep/drop separator behavior where relevant.

Initial implementations:

- character splitter;
- recursive character splitter;
- token-aware splitter using tokenizer protocol;
- generic structure-aware extension hook.

** Splitter safety invariants

For every non-empty input:

1. every iteration consumes positive input or terminates;
2. =overlap < chunk-size= unless a custom strategy explicitly proves forward progress;
3. produced chunk count is bounded by configured maximum;
4. chunk order follows source order;
5. provenance maps each output back to its parent.

Representative constructor:

#+begin_src lisp
(make-recursive-character-splitter
 :chunk-size 1200
 :overlap 120
 :separators '("\n\n" "\n" " " "")
 :max-chunks 100000)
#+end_src

Chunking must guarantee forward progress even when one unit exceeds chunk size.

* Tokenizer protocol

Do not couple splitters to one model tokenizer package.

#+begin_src lisp
(defclass tokenizer () ())

(defgeneric token-count (tokenizer text))
(defgeneric encode-tokens (tokenizer text))
(defgeneric decode-tokens (tokenizer tokens))
(defgeneric tokenizer-identity (tokenizer))
#+end_src

A simple approximate/default character length function remains usable without tokenizer integrations.

* Embedding protocol

#+begin_src lisp
(defclass embedding-model () ())

(defgeneric embed-query (model text &key context options))
(defgeneric embed-documents (model texts &key context options))
(defgeneric embed-query-async (model text &key context options))
(defgeneric embed-documents-async (model texts &key context options))
#+end_src

Result carries vectors plus model/provider identity, dimensions, usage and metadata.

#+begin_src lisp
(defclass embedding-result ()
  ((vectors :initarg :vectors :reader embedding-result-vectors)
   (dimensions :initarg :dimensions :reader embedding-result-dimensions)
   (model :initarg :model :reader embedding-result-model)
   (provider :initarg :provider :reader embedding-result-provider)
   (usage :initarg :usage :initform nil :reader embedding-result-usage)
   (extensions :initarg :extensions :initform nil
               :reader embedding-result-extensions)))
#+end_src

Validation before returning a successful result:

- vector count equals input count;
- dimensions are positive and equal for every vector;
- all numeric elements are finite;
- dimensions match requested/declared dimension where applicable;
- total element count obeys configured resource bounds.

OpenRouter is the first remote implementation. Embedding requests reuse provider auth/config/model discovery from Design 002.

* Embedding batching

Batching is explicit because provider limits vary.

#+begin_src lisp
(embed-documents model texts
                 :options (make-embedding-options
                           :batch-size 64
                           :max-concurrency 4))
#+end_src

The adapter may reduce a requested batch size to provider limits but must not exceed caller hard limits. Result order always matches input order even if batches execute concurrently.

* Embedding cache

A cache wrapper decorates any embedding model.

Cache key includes:

- embedding model/provider identity;
- relevant embedding options/dimension/input type;
- normalized input bytes/text hash;
- cache schema version.

#+begin_src lisp
(defun embedding-cache-key (model options text)
  (list :version 1
        :model (embedding-model-identity model)
        :options (embedding-cache-relevant-options options)
        :input-sha256 (sha256-utf8 text)))
#+end_src

Document and query caching may use separate namespaces because providers can distinguish input types. Cache values include vector and necessary identity metadata. Never cache secrets/provider headers.

* Store protocol

Generic key/value store operations:

#+begin_src lisp
(defclass byte-store () ())

(defgeneric store-mget (store namespace keys &key context))
(defgeneric store-mset (store namespace pairs &key context))
(defgeneric store-mdelete (store namespace keys &key context))
(defgeneric store-yield-keys (store namespace &key prefix context))
#+end_src

Keys are strings/octet keys with a documented normalized representation. Values are caller-defined serializable values/octets at this layer.

Initial in-memory store is lock-safe and deterministic. Persistent adapters remain separate integrations.

* Vector-store protocol

#+begin_src lisp
(defclass vector-store () ())

(defgeneric vector-store-add (store documents &key ids vectors context))
(defgeneric vector-store-delete (store ids &key context))
(defgeneric similarity-search (store query &key k filter context))
(defgeneric similarity-search-vector (store vector &key k filter context))
(defgeneric similarity-search-with-score (store query &key k filter context))
#+end_src

A vector store declares dimension, metric and embedding model requirements.

#+begin_src lisp
(defgeneric vector-store-dimension (store))
(defgeneric vector-store-metric (store))
#+end_src

Incompatible dimension insertion signals a typed error before mutating state.

* Search result and score semantics

Backends return canonical retrieval results:

#+begin_src lisp
(defclass retrieval-result ()
  ((document :initarg :document :reader retrieval-result-document)
   (score :initarg :score :initform nil :reader retrieval-result-score)
   (rank :initarg :rank :reader retrieval-result-rank)
   (metadata :initarg :metadata :initform nil :reader retrieval-result-metadata)))
#+end_src

Canonical =score= means “larger is more similar/relevant” for the standard vector-store API.

Reference normalization:

- cosine similarity -> cosine value, larger better;
- dot product -> dot value, larger better;
- Euclidean distance -> convert to a documented monotonic similarity such as =1 / (1 + distance)=, while preserving raw distance in metadata.

Backends whose native score cannot be normalized reliably must expose the raw score/metric in metadata and either implement the canonical ordering contract or use a backend-specific advanced method. Do not mix “smaller is better” and “larger is better” behind one method silently.

* In-memory vector store

Reference backend stores vectors/documents in process memory with thread-safe mutation and exact search.

Required metrics:

- cosine similarity;
- dot product;
- Euclidean distance converted/documented as ranking score.

Representative construction:

#+begin_src lisp
(let ((store (make-memory-vector-store
              :dimension 1536
              :metric :cosine
              :embedding-model embeddings
              :max-vectors 100000)))
  (vector-store-add store docs)
  (similarity-search store "Common Lisp agents" :k 8))
#+end_src

Search is deterministic under ties using stable id, falling back to insertion ordinal when ids are absent.

This backend is for correctness/tests/small workloads, not a claim of production ANN scalability.

* Portable filters

First filter language supports a conservative portable AST:

#+begin_src lisp
(:and
  (:= :source "manual")
  (:>= :year 2025)
  (:in :language ("en" "fr"))
  (:exists :author))
#+end_src

Operators:

- =:=, =:/==;
- numeric/string =:< :<= :> :>==;
- =:in= / =:not-in=;
- =:and :or :not=;
- =:exists=.

Backend behavior is explicit:

- =:pushdown-required= -> signal if backend cannot implement filter natively;
- =:post-filter-allowed= -> backend may retrieve a bounded candidate set then apply canonical filter locally;
- =:unsupported= -> typed failure.

Post-filtering must expose the candidate expansion policy/limit; it cannot scan an unbounded remote store invisibly.

* Retriever protocol

Retriever invocation maps a query/input to ordered retrieval results/documents.

#+begin_src lisp
(defclass retriever () ())

(defgeneric retrieve (retriever query &key context options))
(defgeneric retrieve-async (retriever query &key context options))
(defgeneric retrieve-batch (retriever queries &key context options))
#+end_src

Implementations:

- vector-store retriever;
- callable/function retriever adapter;
- composed retriever hooks for later FTS/graph/SQL systems.

Representative vector retriever:

#+begin_src lisp
(let ((retriever (make-vector-store-retriever
                  store
                  :k 6
                  :filter '(:= :project "llm-agent-cl"))))
  (retrieve retriever "checkpoint semantics"))
#+end_src

Optional stream is only for retrievers that naturally support progressive results; vector retrieval does not need fake streaming.

* RAG helpers

Provide composable helpers rather than a mandatory opaque “RAG chain” object:

- retrieve context;
- format documents with configurable separator/template;
- attach source metadata/citations to runtime state;
- create retriever-as-tool;
- create retrieval graph node;
- convenience =retrieve-and-generate= layered above these protocols.

** Direct composition

#+begin_src lisp
(let* ((results (retrieve retriever question))
       (context-text (format-retrieval-context results
                                               :include-source t))
       (messages (list
                  (make-system-message "Answer using supplied context.")
                  (make-user-message
                   (format nil "Context:~%~A~%~%Question: ~A"
                           context-text question)))))
  (invoke-model model messages))
#+end_src

** Retriever as tool

#+begin_src lisp
(make-retriever-tool
 :name "search_docs"
 :retriever retriever
 :description "Search project documentation")
#+end_src

** Retriever as graph node

#+begin_src lisp
(defun retrieval-node (state context)
  (let ((results (retrieve (context-dependency context :retriever)
                           (state-ref state :query)
                           :context context)))
    `((:retrieved-documents . ,results))))
#+end_src

This lets retrieval work standalone, in a tool-calling agent, or in a graph.

* Concurrency and resource limits

Explicit bounds include:

- loader response/file bytes;
- maximum documents per load;
- maximum chunks per input/operation;
- maximum individual document/chunk bytes;
- embedding batch size/concurrency;
- maximum embedding dimensions/total vector elements;
- vector count for in-memory store;
- retrieval =k= maximum;
- post-filter candidate expansion;
- lazy-loader channel capacity;
- deadline/cancellation.

Constructors reject invalid limits early. No dangerous dimension should interpret zero as unlimited implicitly.

* Failure semantics

Typed retrieval conditions should distinguish at least:

- loader source/read/encoding/content-type/size failure;
- splitter invalid configuration/non-progress/limit failure;
- embedding provider/dimension/value failure;
- cache corruption/version mismatch;
- store failure;
- vector dimension/metric/filter failure;
- retriever failure.

Store mutation APIs should validate all input vectors/documents first where practical so one malformed element does not produce an accidental partial insert. Backends that cannot provide atomic batch mutation must document partial-write behavior explicitly.

12. parity closure and additional integrations required by tests.

* Rejected alternatives

** Couple documents to one vector database schema

Rejected because document provenance/loaders/retrievers must remain useful independently of a specific persistence backend.

** Return raw provider embedding JSON

Rejected because callers and vector stores need stable ordered vectors/dimension/usage semantics.

** Treat vector scores as backend-native opaque numbers in the common API

Rejected because opposite score orientations cause subtle ranking bugs. Canonical common search uses larger-is-better semantics.

** Silently post-filter unsupported metadata expressions

Rejected because candidate expansion can alter performance/recall drastically. Post-filtering requires explicit policy and bounds.

** Build one monolithic RAG chain abstraction first

Rejected because the required capability class is composable loaders/splitters/embeddings/stores/retrievers usable by graphs/tools as well as simple RAG.

* Open design questions for maintainer approval

1. Canonical document text slot name. Keep =page-content= for LangChain familiarity or prefer =content=. Recommendation: export =document-content= accessor even if internal slot remains page-content.
2. First persistent store/vector integration after in-memory reference. Do not select one until dependency/reliability work is justified.
3. Exact Euclidean canonical similarity conversion. Recommendation: =1/(1+d)= because it is bounded, monotonic and simple; raw distance remains metadata.
4. Whether vector-store =add= computes embeddings automatically when an embedding model is configured, or require distinct =add-documents= and =add-vectors=. Recommendation: distinct explicit methods plus ergonomic convenience wrapper.
5. Whether HTML extraction dependency belongs in the first retrieval implementation slice. Protocol is required; concrete dependency can land after core deterministic pieces.

* Footnotes and Glossary

- *ANN*: approximate nearest-neighbor search.
- *Provenance*: information connecting a derived chunk/document to its originating source/document.
- *Embedding cache*: store-backed decorator avoiding recomputation for identical model/options/input.
- *Canonical similarity score*: normalized common score whose ordering is always larger-is-better.
