* Research question

Does a real asynchronous Common Lisp HTTP client exist that can support llm-agent-cl, and what must be done before it is safe to use for production provider traffic?

* Answer and maintainer decision

Yes: Carrier exists. It is a lightweight asynchronous Common Lisp HTTP client built on =cl-async= and =fast-http=. Its upstream ASDF system identifies version =0.1.1= under the MIT license. Its request API returns a Blackbird promise and exposes callbacks for response headers, incremental body bytes and completion.

The maintainer has now forked it at =https://github.com/lost-rob0t/carrier= and explicitly selected that fork as the async library to maintain and fix. GitHub reports the repository as a fork of =orthecreedence/carrier=. At research time the fork's =master= tree is exactly =95ea9edba80f67598bfde550a170a2f787970223=, the same upstream tree, so the hardening work has not begun.

Carrier resolves the async-client question but does **not** satisfy the production security/lifecycle contract unchanged.

* Verified architecture

Carrier's current request path:

1. parses a URL with Quri;
2. serializes an HTTP/1.1 request;
3. opens a non-blocking =cl-async= TCP or =cl-async-ssl= TLS connection;
4. sends request data;
5. feeds response bytes to =fast-http=;
6. emits parsed response headers;
7. emits response body byte slices incrementally;
8. resolves a Blackbird promise after response completion;
9. closes the socket.

This response-byte model is sufficient for OpenRouter SSE. HTTP/2 is not required for semantic streaming correctness.

* Critical TLS finding

Carrier's HTTPS path delegates to =cl-async-ssl:tcp-ssl-connect=. Current =cl-async-ssl= creates a client SSL context, loads default verify paths and then configures verification with =SSL_VERIFY_NONE=. The source also contains a TODO for better verification support.

SNI is set but does not authenticate the remote peer. Sending OpenRouter or other provider API keys over this baseline would fail the project's production security requirement.

The maintained fork must fail closed. The hardening design requires:

- peer certificate-chain verification enabled;
- hostname verification against the requested host;
- SNI set to that same host;
- CA trust sourced from system/configured trust stores;
- verification failure before application response data is delivered;
- no accidental “insecure=true” default path;
- local TLS fixtures proving valid, expired, self-signed, wrong-host and untrusted-chain behavior.

If the current =cl-async-ssl= public surface cannot express safe verification, Carrier may encapsulate the necessary OpenSSL/CFFI compatibility code internally or a separately approved dependency patch may be required. llm-agent-cl must never monkey-patch private TLS symbols itself.

* Cancellation and request handle

The maintained fork should add a request handle rather than only returning a bare promise. The handle needs:

- request id;
- terminal state;
- promise/result linkage;
- socket/connection ownership;
- cancellation operation;
- deadline/timer state;
- response metadata/byte counters;
- pool lease if connection reuse is active.

Cancellation must be idempotent and race-safe with EOF, timeout, parser completion and redirect. Exactly one terminal completion/rejection is permitted.

* Connection/TLS reuse

The fork should introduce a client object owning bounded per-origin connection pools and reusable TLS contexts. Initial HTTP/1.1 reuse can be sequential per connection; pipelining is not required. Pool keys must include scheme, host, port and relevant TLS/proxy policy.

Issue #25 documents the cost of recreating SSL contexts under load. Reusing a correctly configured TLS context is therefore both a performance and lifecycle requirement.

* Request serialization

The existing request builder creates a string and converts request body bytes through text operations. A generic production HTTP client must serialize headers to octets and append/write body octets without lossy text round trips. Content-Length/chunked upload semantics must be explicit.

Streaming request bodies should use a producer/callback/stream interface with bounded buffering and cancellation awareness.

* Redirect security

The fork must define method/body behavior for 301/302/303/307/308, relative Location resolution, redirect loop limits and origin changes. Sensitive headers such as Authorization must be removed automatically when a redirect crosses origin unless the caller explicitly provides a narrowly scoped policy.

* Backward compatibility

Carrier is a standalone library, not an llm-agent-cl internal module. The hardening work should preserve the existing =carrier:request= style where practical. A recommended evolution is:

- keep =request= as a compatibility convenience returning the familiar promise/results;
- add a client/request-handle API for production lifecycle control;
- implement old =request= through the new client core so security fixes apply to both paths;
- document behavior changes where insecure historical behavior cannot be retained.

Security takes precedence over bug-for-bug compatibility.

* Release and ownership policy

Before llm-agent-cl consumes the fork as its production async adapter:

1. Carrier gets its own CI and deterministic test suite.
2. TLS failure/success fixtures pass.
3. cancellation/deadline races pass under repetition.
4. connection reuse and shutdown leak tests pass.
5. redirects and binary bodies pass.
6. a maintained-fork release/tag is cut (design proposes =0.2.0=, subject to approval).
7. llm-agent-cl pins/tests that release through its transport conformance suite.

* Historical libcurl research

libcurl multi remains technically strong contingency evidence: it is event-driven, supports many concurrent transfers, mature TLS and connection reuse. It is **not** the active implementation direction after the maintainer's Carrier decision. It should not be introduced merely because Carrier hardening is non-trivial; changing direction requires explicit review.
