* Boundary conclusion

The project is a layered embeddable library. It does not own a daemon, web UI, hosted agent service, global database, StarIntel actor runtime, or mandatory scheduler. Applications compose those around the library.

This boundary does **not** prohibit ergonomic process-wide defaults. The distinction is between an embeddable core whose dependencies/configuration can always be explicit, and optional convenience state intentionally configured by an end user for REPLs, examples or quick tests.

* Layers implied by research

These are dependency directions reflected in the accompanying designs:

1. **Canonical values and errors** — messages, content blocks, usage, tool calls/results, documents, embeddings, stream events and conditions.
2. **Execution primitives** — cancellation, deadlines, future/result semantics, bounded channels, middleware/event hooks.
3. **Configuration/runtime context** — explicit client/runtime config plus scoped/process convenience defaults.
4. **HTTP transports** — Dexador sync and maintained =lost-rob0t/carrier= async adapters.
5. **Provider contracts/adapters** — OpenRouter first; provider capabilities/extensions isolated here.
6. **Tool + structured-output layer** — JSON Schema validation, execution, result correlation.
7. **Graph/state runtime** — reducers, nodes/edges, Send/Command, supersteps, checkpoints, interrupts, subgraphs, time travel.
8. **High-level agent layer** — model/tool loop built on graph primitives.
9. **Retrieval/data plane** — documents, loaders, splitters, embeddings, stores, vector stores and retrievers; first-major-milestone core package family.
10. **MCP adapters** — tools/resources/prompts through canonical contracts.
11. **Optional integrations** — persistent checkpointers/stores, tracing exporters and application-specific adapters.

* Why graph/state must precede high-level agent convenience

LangChain currently builds its high-level agent behavior on LangGraph. Persistence, interrupts, memory, streaming and time travel all rely on explicit state transitions. Implementing a recursive model/tool loop first and attempting to retrofit checkpoint semantics later would force breaking changes. The designs therefore put the graph/state execution contract under the high-level agent API from the first implementation sequence.

* Why retrieval is not optional later work

Current LangChain treats document processing, embeddings, retrievers and vector stores as first-class component categories and its retrieval pipeline composes them directly. The maintainer explicitly requires these in the first major parity milestone. They can live in separate ASDF systems/packages so lightweight consumers do not load every integration, but the release milestone is not complete without them.

* Provider independence rule

OpenRouter is the first provider, not the canonical wire model. OpenAI-compatible JSON is useful adapter input/output but cannot define the core because providers vary in reasoning, multimodal, tools, caching, citations, routing and metadata. Unknown provider-native data needs an explicit extension map.

* Explicit core plus intentional defaults

The previous “No hidden global state” language was too absolute. The approved model is:

- core constructors and operations accept explicit configuration;
- runtime/context objects carry caller-owned dependencies and state;
- dynamic special variables provide scoped defaults for REPL/tests;
- a small process-wide default registry/configuration object may be intentionally mutated by callers;
- environment variables can provide provider-standard convenience defaults;
- explicit values always have higher precedence than defaults;
- defaults are inspectable/resettable and tests can run with a fresh default context;
- secrets are redacted and never serialized implicitly.

Conversation state, checkpoint state and tool side effects must not silently fall back to unrelated process-global state. Convenience globals are for defaults/configuration, not hidden execution history.

* Maintained Carrier boundary

The production async dependency is =lost-rob0t/carrier=. Carrier remains a standalone HTTP library; llm-agent-cl must not inject provider, agent or StarIntel concepts into it. The fork hardening design is maintained in this auto-research repository and must be approved before changes land in Carrier.

* Dependency conclusions

The dependency research selects:

- =com.inuoe.jzon= as the JSON parser/writer candidate;
- =cl-jschema= behind a project-owned validator protocol, with conformance gaps tested before production claims;
- =bordeaux-threads= for portable locks/condition primitives;
- =lparallel= for bounded worker pools, parallel tools/graph branches and future-like task execution;
- Blackbird remains internal to Carrier adaptation rather than becoming llm-agent-cl's public async type.

See research 009 for constraints and caveats.

* Footnotes and Glossary

- *Embedding*: using the library inside another application/process rather than requiring an external service.
- *Extension map*: explicit storage for provider-native fields not standardized by canonical types.
- *Intentional default*: caller-configured convenience state with documented precedence and reset behavior.
