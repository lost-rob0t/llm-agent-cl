* Boundary conclusion

The project should be a layered embeddable library. It should not own a daemon, web UI, agent hosting service, global database, StarIntel actor runtime, or mandatory scheduler. Applications compose those around the library.

* Layers implied by research

These are dependency directions for a future design, not implementation package names:

1. **Canonical values and errors** — messages, content blocks, usage, tool calls/results, stream events, conditions.
2. **Execution primitives** — cancellation, deadlines, sync/async result semantics, middleware/event hooks.
3. **HTTP transports** — Dexador sync plus a production async backend conforming to the same contract; Carrier is the native Common Lisp reference implementation, with hardening or libcurl-multi replacement required before production.
4. **Provider contracts/adapters** — OpenRouter first; provider capabilities and extensions isolated here.
5. **Tool + structured-output layer** — schema validation, execution, result correlation.
6. **High-level agent loop** — repeated model/tool turns, budgets/limits, multi-turn state.
7. **Low-level graph/state layer** — deterministic/agentic nodes, routing, checkpoints, interrupts, subgraphs, parallelism.
8. **MCP adapters** — translate MCP tools/resources/prompts through existing canonical contracts.
9. **Optional integrations** — persistence backends, tracing exporters, retrieval/vector systems, application adapters.

* Why the graph/state layer belongs in the library

LangChain currently builds its high-level agents on LangGraph and gains persistence, durable execution, and HITL from that lower layer. If =llm-agent-cl= implements only a recursive tool loop first and treats explicit state/checkpointing as an application concern, later parity would require breaking core execution semantics. Therefore state transitions, cancellation, event streaming, and resumability need to be designed before implementation even when the first milestone uses in-memory state.

* Provider independence rule

OpenRouter is the first provider, not the canonical wire model. OpenAI-compatible JSON is useful adapter input/output but cannot define the full core because other providers expose different reasoning, multimodal, tool, cache, citation, and metadata structures. Unknown provider-native data needs a deliberate extension escape hatch.

* No hidden global state

Provider credentials, default models, tool registries, conversation state, checkpoint stores, middleware stacks, and transport clients should be explicit values/configuration supplied by callers. Thread-local/dynamic conveniences may exist later, but the core contract must remain testable and embeddable.

* First future design prerequisites

Before writing Common Lisp runtime code:

- maintainer approves the research scope;
- async transport design selects either a hardened Carrier path or a libcurl-multi client and defines verified TLS/cancellation/reuse semantics;
- OpenRouter structured-output/capability field research is completed;
- a design defines canonical values/errors and sync/async semantics;
- dependency choices for JSON + JSON Schema + concurrency primitives are researched for license/maintenance/portability.

* Footnotes and Glossary

- *Embedding*: using the library inside another application/process rather than requiring an external service.
- *Extension escape hatch*: explicit storage for provider-native fields that canonical types do not standardize.
