* Verified facts

OpenRouter exposes an OpenAI-compatible HTTP API and standardizes tool calling across models/providers. The stable chat-completions path supports =messages=, model selection, tools and =stream: true=. Streaming uses Server-Sent Events (SSE). OpenRouter can emit SSE comment lines as keepalive/processing signals; consumers must ignore valid SSE comments rather than parse every line as JSON.

Streaming tool calls arrive incrementally and require assembly by tool-call index/ID before arguments are parsed as complete JSON. A final chunk can include usage metadata. Errors that occur after HTTP 200 may be delivered inside the stream as a terminal error payload. The generation ID exposed in response metadata/headers should be preserved as provider-native metadata.

OpenRouter documents stream cancellation by closing/aborting the connection; immediate upstream cancellation support varies by provider. This reinforces the requirement for a real cancellable async transport handle.

The Responses API remains documented as beta. It is useful as an optional endpoint family but should not be the sole production foundation for the first adapter. Chat Completions remains the baseline provider contract; Responses support should be capability/feature-flagged until its stability contract changes.

* Authentication and configuration decision

The earlier wording “authentication from caller-supplied secret/config only” was too restrictive for the maintainer's desired REPL/development experience.

The provider design must support a deterministic resolution chain:

1. explicit per-call credential/config override;
2. explicit provider/client configuration object;
3. dynamically scoped defaults (for tests/REPL blocks);
4. intentionally configured process-wide convenience defaults;
5. provider-standard environment fallback such as =OPENROUTER_API_KEY=;
6. otherwise signal a typed missing-credential condition.

There must never be a library-shipped hard-coded credential. Convenience defaults are allowed, but resolved secrets must be redacted from object printers, logs, conditions, traces and serialized checkpoints.

This is similar in spirit to current LangChain quickstarts, which commonly support environment-variable provider keys while also allowing explicit model/client configuration.

* Structured outputs: field-level gap closed

OpenRouter's current Structured Outputs documentation specifies provider-native JSON Schema enforcement through =response_format=:

#+begin_src json
{
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "result",
      "strict": true,
      "schema": {"type": "object"}
    }
  }
}
#+end_src

Current guidance recommends =strict: true=. Structured outputs are model-dependent. The Models API exposes each model's =supported_parameters=, including values such as =structured_outputs= and =response_format=. Provider routing can use =require_parameters: true= so a request requiring structured output is not silently sent to an endpoint lacking support.

Structured outputs can also be streamed; the stream contains partial JSON that becomes schema-valid when complete. llm-agent-cl therefore needs separate states for incremental structured text and final schema-validated value.

For tools, provider/model strictness and beta provider headers remain provider-native extensions rather than canonical core fields. Unknown routing/provider features must survive through the provider extension map.

* Model discovery and capability profiles

OpenRouter's Models API can filter by =supported_parameters= and output modality. Model records expose architecture/input/output modalities, context length, pricing, supported parameters and provider metadata. llm-agent-cl should normalize a conservative capability profile while preserving the full provider-native record.

The cache must have explicit staleness/refresh controls. Capability absence is not proof of permanent lack of support; stale caches must be observable and refreshable.

* Embeddings

OpenRouter now exposes a first-class embeddings API at =POST /api/v1/embeddings= and an embeddings model listing endpoint. Requests support a single input or batch input and model selection, with optional dimensions, encoding format, input type and provider routing. Responses include indexed embedding vectors plus model and usage metadata.

OpenRouter's embeddings documentation states that embeddings are returned as complete responses rather than streamed. This provider therefore satisfies the first remote embedding-model implementation required by the LangChain parity milestone.

The OpenRouter provider adapter should implement both chat-model and embedding-model protocols without making the core assume all providers expose both through the same endpoint family.

* Required provider adapter behaviors

- Deterministic credential/config resolution as defined above.
- Model and embedding-model discovery/capability caching with explicit staleness policy.
- Canonical request translation from provider-neutral messages/content/tools/structured-output requests.
- Provider extension map for OpenRouter routing and metadata fields.
- Non-stream and stream response normalization.
- Embedding single/batch normalization.
- Preservation of usage, finish reason, model/provider metadata, tool-call IDs and generation identifiers.
- Typed HTTP errors, provider errors, malformed responses and mid-stream errors.
- Cancellation and deadline propagation to the HTTP transport.
- Explicit unsupported-capability errors rather than silent field dropping.
- Retry classification that distinguishes safe pre-submit failures from ambiguous or partially streamed submissions.
- Secret redaction in all printable/observable objects.

* Tool loop requirements

OpenRouter follows the common tool-call loop: append the assistant tool-call message to conversation history, execute each requested tool, append correlated tool results, then invoke the model again. The core agent/graph layer, not the OpenRouter adapter, owns this loop.

* Footnotes and Glossary

- *SSE*: Server-Sent Events, the event framing used by OpenRouter streaming.
- *Ambiguous submission*: a request whose server-side execution status is unknown after a transport failure.
- *Capability profile*: normalized provider/model features used for routing and validation, with provider-native metadata retained alongside it.
